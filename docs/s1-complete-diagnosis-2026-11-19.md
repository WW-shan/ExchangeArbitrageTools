# S1 完整诊断：数据、根因、结论

> 2026-11-19。基于 24h 实盘 + 全部历史盘口。这份文档回答三个问题：
> 亏在哪、修了什么、还剩什么没解决。

## 一、亏在哪（三个独立原因，都已定位）

### 1.1 代码缺陷：买到了不卖（已修）

| 指标 | 修复前 24h |
| --- | --- |
| S1 买入成交 | 27 笔 |
| S1 卖出成交 | **1 笔** |
| 结果 | **-2.54 USDT** |

`coordinator.ts` 在买腿成交后重拉卖盘，若重算利润 <= 0 就 `SAFE_STOP`，
**卖腿从未提交**。等于「亏了就不卖」。

修复：买腿已成交后，卖腿必执行，只有亏损超过 `max_post_fill_exit_loss_usd`（0.5U）才停。

### 1.2 费率配置缺失：Bitget 返佣没写进去（已修）

| 交易所 | 配置 | 实际 |
| --- | --- | --- |
| Gate | 9.9 bps × 30% = 2.97 bps | 正确 |
| Bitget | 10 bps × 100% = **10 bps** | 应为 80% 返佣 = **2 bps** |

往返成本被高估 **8 bps**（12.97 vs 4.97）。
对一个 60 bps 的价差，这是「赚」和「亏」的分界线。

### 1.3 标的选择：WARD 大部分时间没有价差（未解决）

这是最根本的问题。24h 内 WARD 的净价差（已扣 4.97 bps 手续费）：

| 时段 | 平均净价差 |
| --- | --- |
| 12:00 | **-204 bps** |
| 13:00 | **-150 bps** |
| 14:00 | **-178 bps** |
| 15:00 | -86 bps |
| 16:00 | -85 bps |
| 17:00 | **-134 bps** |
| 18:00 | **-144 bps** |

**大部分时间是负的。** 只有 336 个 valid 样本（占全部样本的 0.3%）里才有正价差。

## 二、机会到底有多少（诚实统计）

24h 内 WARD 的有效机会（episode）：

| 方向 | 次数 | 总时长 | 单次最大利润 |
| --- | --- | --- | --- |
| **gateio → bitget** | 30 | 1002 s | 0.1157 U |
| bitget → gateio | 9 | 16 s | 0.0288 U |

关键：**方向几乎永远是 gate→bitget**（30:9），因为 Gate 的 ask 长期低于 Bitget 的 bid。

持续时长分布：

| 分位 | 时长 |
| --- | --- |
| p50 | 2.6 s |
| p90 | 90 s |
| max | 219 s |

**39 个 episode 里，20 个超过我们 2.6s 的端到端延迟，15 个超过 5.4s 的 p90 延迟。**

结论：机会存在，但：
- 单笔只有 **0.03~0.12 USDT**；
- 中位持续 2.6 秒，刚好卡在我们的延迟线上；
- 方向单一（gate→bitget），意味着库存会持续向一侧倾斜。

## 三、修复后的预期

修复了两个 bug（卖腿 + 费率）后：

- 原来「买了不卖」的 26 笔，现在会正常卖出；
- 每笔成本降低 8 bps；
- 按历史 episode 估算，**20 个可执行窗口 × 平均 0.05U = 约 1 USDT/天**（理想情况）。

这不是暴利，但至少不再是负的。

## 四、仍然没解决的问题

### 4.1 延迟是硬约束

| 环节 | p50 | p90 |
| --- | --- | --- |
| 拉盘口 | 227 ms | 1888 ms |
| 拉余额 | 165 ms | 2026 ms |
| 纯计算 | 1 ms | 217 ms |
| **端到端** | **2600 ms** | **5384 ms** |

而 Bitget 的 ask 在 1 秒后只有 **51%** 还在原位。
**我们重拉卖盘时，一半的概率价格已经变了。** 这是结构性的。

### 4.2 WARD 的价差窗口太短

中位 2.6 秒，正好等于我们的 p50 延迟。
意味着：**一半的机会我们赶不上。**

### 4.3 单标的集中风险

只做 WARD 意味着没有分散。WARD 没价差时，系统就是空转。

## 五、真正该做什么（按价值排序）

### 优先级 1：换更有价差的标的（最高价值）

我们的插针扫描器已经证明：**大价差 ≠ 机会**（BREV 12% 是因为不能提币，WEEX 是数据延迟 600 秒）。

但扫描器现在有了正确的过滤链：
1. 可双向提币（425/1866 通过）
2. 数据延迟 < 5s
3. 盘口有成交量
4. 价差 > 阈值

**下一步应该在 425 个可搬币里，找那些价差窗口 > 10 秒的**，而不是继续在 WARD 上挤。

### 优先级 2：减少一次重拉盘口

现在的串行模式：买 → 重拉卖盘 → 卖。这个重拉是 1.5 秒。
如果改成「买的同时预挂卖单」，能省掉这 1.5 秒。但这需要 FOK 原子性验证。

### 优先级 3：降低拉余额的延迟

拉余额 p50 165ms、p90 2026ms，而它每次执行都要做。
缓存已经做了（`preflight-cache.ts`），但 p90 仍然 2 秒。

## 六、明确不该做的

- **不要**因为「想抓插针」而放宽安全逻辑。
- **不要**在没有验证的情况下把 `max_notional` 从 0 改回去——修好卖腿后需要重新观察。
- **不要**相信任何「回测 +1117U」的结论——那是用失效历史盘口算出来的。
