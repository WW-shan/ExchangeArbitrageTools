# S1 两腿执行、库存风险与“价差回归”

最后核对：2026-10-27。本文只讨论现有 S1 CEX-CEX 现货执行链，不启用实盘。

## 1. 先说结论

**不能确定后面一定回归。**

跨交易所 S1 不是“买一边、等另一边价格回来”的回归交易。它的目标是把
Gate 的低价买腿和 Hotcoin 的高价卖腿同时或快速完成，两腿成交后价差就已经
落袋，后面价差回不回归不重要。

真正需要“回归”的是只完成一条腿的情况：

- 只在 Gate 买到了币，Hotcoin 没卖掉：你持有现货多头，价格可能继续跌。
- 只在 Hotcoin 卖掉了币，Gate 没买到：你少了一部分现货库存，价格可能继续涨。

这两种情况都只能按风险库存处理，不能假设价格会自动回来。

2026-10-27 的 TBK 就是例子：Gate 买、Hotcoin 卖的方向一度有约 360 bps
毛边，约 104 USDT 容量；但十分钟后再看已经反转成约 -367 bps。它不是
“等一等就会回来”，而是 Hotcoin 的 bid 被吃掉或撤掉了。

## 2. 当前代码实际怎么下两腿

现有执行器在 `apps/executor/src/coordinator.ts`，顺序是：

1. 刷新两边订单簿和两边余额。
2. 重新计算深度、手续费、利润、精度和最小额。
3. 先提交腿 1：在 Gate 买入。
4. 查询腿 1 的真实成交量和成交均价。
5. 用腿 1 的**实际成交量**，重新抓 Hotcoin 卖盘。
6. 重新计算腿 2 的深度和预计利润。
7. 再提交腿 2：在 Hotcoin 卖出。
8. 两腿都完整成交才记为 `CLOSED`。

关键点：

- 腿 1 的请求价是买入侧最差可成交 ask；腿 2 的请求价是卖出侧最差可成交 bid。
- 腿 2 数量永远来自腿 1 实际成交，不会用计划数量。
- 腿 1 部分成交时，代码会尝试撤掉剩余，只对实际成交部分做腿 2。
- 腿 1 未知、腿 2 拒绝、腿 2 部分成交，都会进入 `SAFE_STOP` 并记录
  `unhedged_inventory`。
- 当前没有自动 flatten，也没有自动“等回归”。只是记录剩余库存和风险事件。

因此当前实现是**先买后卖的串行两腿**，不是跨交易所原子成交。

## 3. 为什么现在还不能直接实盘

代码支持 IOC 或 FOK，但 `config/live-test.toml` 里：

```toml
ioc_venues = []
fok_venues = []
```

执行前会检查两边是否至少有一边支持 IOC 或 FOK；当前配置会触发
`ioc_or_fok_unsupported`，preflight 失败。也就是说：

- 两腿执行代码路径存在并通过了模拟测试。
- Gate 和 Hotcoin 的真实 IOC/FOK 行为还没有用私有 API 验证。
- 没有真实 key、真实余额、真实下单、撤单、部分成交对账证据。

在当前状态下不能把 `live_enabled` 打开。

## 4. 四种可选执行方式

| 方式                                     | 前提                                     | 优点                                     | 主要风险                                          | 当前状态           |
| ---------------------------------------- | ---------------------------------------- | ---------------------------------------- | ------------------------------------------------- | ------------------ |
| 先买后卖，串行                           | Gate 有 USDT，Hotcoin 预先有 base        | 两腿数量最容易对齐；先买不会产生借币空头 | 低流动性卖腿 bid 可能在第二次抓盘前消失           | 已实现，默认       |
| 先卖后买，串行                           | Hotcoin 预先有 base                      | 可以先锁住稀薄的卖腿 bid                 | 卖完后 Gate 买腿失败，会少库存/变成空头暴露       | 未实现             |
| 两腿同时 IOC/FOK                         | 两边都有库存，两个场所都支持可靠 IOC/FOK | 减少腿间延迟                             | 仍非原子；一边成交一边不成交会产生未对冲库存      | 未实现             |
| 无库存搬砖：Gate 买、提币到 Hotcoin 再卖 | 充提开启、网络可用、到账时间可接受       | 不需要预先在 Hotcoin 放币                | 提币费、到账延迟、价格在到账前消失、合约/网络风险 | 未实现，不建议先做 |

### 为什么默认先买后卖

先买后卖失败时，最坏情况是持有 base 多头。它可以用现有库存、后续卖出或
reduce-only 计划处理。先卖后买失败时，如果没有足够的 base 库存，就可能
需要回补，价格上涨时会扩大损失。

但对 TBK 这种 Hotcoin bid 很厚、Gate ask 相对稳定的机会，先买后卖会多一次
卖腿盘口刷新和网络往返。真正有效的改进不是“等回归”，而是：

1. 提前在两边准备好库存。
2. 用很小的固定名义额，避免深度冲击。
3. 对候选做持续 spread tracking，确认 bid 是否还在。
4. 在确认窗口后再决定是否同时/先卖后买。

## 5. 能不能用历史价差判断会回归

可以统计，但不能保证。

新增的 `scripts/track-spread.ts` 会按固定间隔重复抓两边订单簿，记录：

- 毛边、净边、最大可套名义额；
- 有多少个样本扣费后仍然有效；
- 最长连续有效时间；
- 第一次有效后多久失效；
- p50/p95 毛边；
- stale、price_outlier、depth 等阻断原因。

这些指标回答的是“过去几分钟这个价差活了多久”，不是“未来一定回归”。

如果要用作入场条件，建议至少要求：

- 连续 N 个样本满足 `maxEligibleNotional >= 最小下单额`；
- 没有 `stale_book`、`price_outlier`、`one_sided_book`；
- 两边真实库存足够；
- 真实费率已经确认；
- 当前价差和过去 p50 相比没有异常放大。

即使全部满足，也只能说明“过去一段时间的持续性较好”，不能说明下一分钟
一定还在。

## 6. TBK/INC 这类低流动性机会的正确做法

以 TBK 为例，Gate 买、Hotcoin 卖需要：

- Gate 有 USDT；
- Hotcoin 预先有 TBK；
- 两边真实 taker 费率；
- Hotcoin TBK 的充提状态和网络已核验；
- 以 `min(市场容量, Hotcoin TBK 库存, Gate USDT 余额)` 作为实际上限。

当前 `analyzeS1Capacity` 算出的 104 USDT 只是**市场可见深度**，不是你的
可用库存。真正的可下单量还要再取库存上限。

小额建议：

- 先用 5 到 20 USDT 级别验证两腿；
- 每次下单前重新抓两腿盘口；
- 不追已消失的 bid；
- 一腿失败立即进入安全停止，不自动等回归；
- 用 `rebalance:plan` 生成 reduce-only 库存处理计划，人工确认后再处理。

## 7. 现有代码的缺口

1. 真实 Gate/Hotcoin IOC/FOK 行为未验证，配置仍为空。
2. 没有同时下两腿或先卖后买的执行模式。
3. 没有自动 flatten/自动补库存；只有 `unhedged_inventory` 记录和
   `rebalance:plan` 计划。
4. 没有用真实余额限制容量。
5. 没有足够长的 spread 历史来估计生存时间/回归概率。
6. 低流动性 REST 快照偶尔 stale；实盘必须用 WS 或执行前重新抓取。

## 8. 命令

```powershell
$env:ARB_CONFIG = 'config/longtail.toml'
$env:ARB_SOCKS_PROXY = 'socks5://127.0.0.1:10808'

# 观察一个候选的价差存活时间；不是收益预测
npm run track:spread -- --base TBK --duration-ms 300000 --interval-ms 3000

# 查看未对冲库存的只读处理计划
npm run rebalance:plan -- --target gateio:USDT=100,hotcoin:USDT=100

# 低流动性发现与容量
npm run scan:longtail -- --max-bases 200 --max-book-candidates 60
```

只有在真实费率、真实库存、真实 IOC/FOK、持续 tracking 和 24 小时只读
soak 全部通过后，才讨论实盘两腿。
