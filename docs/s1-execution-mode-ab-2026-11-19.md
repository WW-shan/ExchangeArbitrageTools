# 执行模式 A/B：parallel_fok vs serial（2026-11-19）

> 24 笔真实已平仓 S1 批次的实测对比。结论：切回 parallel_fok。

## 1. 数据

| 模式 | 笔数 | 累计 | 平均 | 中位 | 最差 |
| --- | --- | --- | --- | --- | --- |
| **parallel_fok** | 18 | **+2271 bps** | **+126 bps** | **+67 bps** | +18 bps |
| serial | 6 | +247 bps | +41 bps | **+1 bps** | 0 bps |

serial 的 6 笔里，4 笔是 **0 bps**：

| 执行 | 结果 |
| --- | --- |
| #1 | 233 bps（正常） |
| #2 / #3 / #4 | **0 bps**（买了没卖掉） |
| #5 | 13 bps |
| #144 | **1 bps**（预期 0.0276，实际 0.0010） |

## 2. #144 的 700 毫秒

```
买单提交  1795053693170   gateio  0.001639 x 5265  -> 全成
卖单提交  1795053693870   bitget  0.001640 x 5265  -> 全成
           相差 700 ms
```

这 700 毫秒里 Bitget 买一从 **0.001646 掉到 0.001640**（-37 bps）。
信号 31.9 bps，卖价滑 37 bps，利润归零。

这不是 bug——系统正确地按新盘口重算并卖出了。
**这是 serial 模式的固有代价：它必须等买单成交、再重新读盘口。**

## 3. parallel_fok 为什么更好

两腿同时提交，卖腿用的是**决策时**的盘口价，不是 700 ms 后的盘口价。

| 批次 | 预期 | 实际 | 捕获率 |
| --- | --- | --- | --- |
| #13 | 0.6534 | 0.7682 | 118% |
| #25 | 0.0084 | 0.0327 | **390%** |
| #26 | 0.0166 | 0.0935 | **562%** |
| #83 | 0.0022 | 0.0072 | **331%** |
| #85 | 0.0097 | 0.0186 | 191% |

捕获率超过 100% 是因为卖腿按挂单量成交时吃到了更好的价位。

## 4. 之前为什么改成 serial，现在为什么改回来

2026-11-18 的记录是「parallel 在 41% 的信号上有一边未成交」。
把 23 笔 parallel 批次逐笔拉出来核对：

| 结果 | 笔数 |
| --- | --- |
| 两腿全成，数量完全相等 | **18** |
| 两腿都没成（无害） | 3 |
| 一边成交一边没成 | **1**（#7，残差 0.8 个币） |

**18/21 是完全干净的。** 那个 41% 来自冻结盘口的假信号——
也就是这次修掉的 12391.31 WARD 挂单那一类。
假信号被挡住后，parallel 的失败率随之消失。

## 5. 安全边界没有放松

- 两腿仍然是 **FOK**，不成交就不留挂单
- 新加的 `sell_book_too_old_at_submit`（1500 ms）现在**同时覆盖 parallel 和 serial**
  （此前它写在 parallel 分支之后，parallel 完全不受保护）
- 状态机对单边成交仍有 reconcile 路径
- `max_post_fill_exit_loss_usd = 0.5` 仍然生效

## 6. 配置变更

```toml
leg_mode = 'parallel_fok'
preflight_hot_book_max_age_ms = 1200   # 必须低于 submit ceiling 1500
```

`preflight_hot_book_max_age_ms` 从 3000 降到 1200：
3000 的窗口会放行 submit 阶段必然被拒的盘口，
实测 #142（1934 ms）和 #143（2838 ms）都白跑了一次 preflight。
